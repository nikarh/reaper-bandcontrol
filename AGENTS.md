# Working on BandControl

Conventions for people and coding agents. The README explains what the project is; PLAN.md has design notes.

## Never commit

- A REAPER license (`*.rk`, ignored). The REAPER test harness copies the user's license into `target/` at runtime.
- Anything from a real band's project: band, member or song names, initials, real project files. The example project
  (`tests/fixtures/Band Project.RPP`) is generated by `scripts/make-band-fixture.py` from invented data; extend the
  generator instead of copying from a real project.

## Commits

[Conventional Commits](https://www.conventionalcommits.org) with a scope where it helps: `feat(android): ...`,
`fix(server): ...`, `docs: ...`, `test: ...`, `chore: ...`, `ci: ...`. Only `feat`, `fix`, `perf` and `docs` end up
in the changelog and the release notes (`cliff.toml`), so write their subject for users: what changed for them, not
how. One logical change per commit.

## Adding a user facing feature

1. Implement it with tests at the cheapest layer that covers it (Rust unit tests, Kotlin JVM tests, then the
   simulator or real REAPER end-to-end tests; see the table in the README).
2. Describe it in `docs/features.toml` (title, a short text for musicians, and the screenshot that shows it).
3. If it is visible in the app, make `ScreenshotTest` (`android/app/src/androidTest/.../ScreenshotTest.kt`) capture
   it under the name used in `features.toml`, from a fixed state of the simulated example project (fixed position,
   fixed meter levels via the simulator's control port, transport stopped). REAPER screenshots are taken by
   `scripts/docs-screenshots.sh reaper`.
4. `mise run docs` renders the README section and the website; `mise run docs:screenshots` regenerates the
   screenshots locally (a phone or `scripts/android-emulator.sh`). On GitHub the Docs workflow does the same and
   opens a pull request.
5. `mise run lint` checks that the README matches `features.toml` and that every referenced screenshot and icon
   exists.

Website structure: every block of `site/index.html` is `<section id="…"><div class="wrap"><h2>…</h2> … </div></section>`
directly in `<main>`; the CSS gives them the same spacing and alternates their background. A block's subsections are
`h3` directly inside its `.wrap`; no other heading levels, and no second `h2` in a block.

Icons on the website: `{{icon:NAME}}` in `site/index.html` inlines `site/icons/NAME.svg`, so it takes the text color.
Platform logos come from [Simple Icons](https://simpleicons.org) (CC0), everything else from
[Lucide](https://lucide.dev) (ISC); keep their markup, minus titles, comments and fixed sizes.

## REAPER versions

The oldest supported and the newest tested REAPER are `min` and `tested` in `[workspace.metadata.reaper]` in
`Cargo.toml`. The extension (load-time warning), CI (the e2e tests against both on every change), the scripts and the
website read them; `mise run lint` fails when the README names other versions. To support a new REAPER: raise
`tested` (the weekly *Newest REAPER* workflow opens an issue when a newer release passes), update the README, and run
`mise run e2e:reaper-versions` for the whole range. A REAPER API function newer than `min` must be optional (looked up
separately in `ffi.rs`, with a fallback), or `min` has to go up.

## Checks before pushing

```sh
mise run lint && mise run test && mise run android:lint && mise run android:test
mise run e2e:reaper          # needs REAPER and cage or Xvfb
mise run android:e2e         # needs a phone or the emulator
```

## Releases

Never edit versions or `CHANGELOG.md` by hand: the *Create a release PR* workflow does both. See
[docs/RELEASING.md](docs/RELEASING.md).
